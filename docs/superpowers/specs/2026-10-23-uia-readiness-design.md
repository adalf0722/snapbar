# UIA 首次選取延後就緒修正

使用者回報 Sublime 正常；ChatGPT 桌面 App 前幾次顯示沒有選字介面，之後相同操作能取得唯讀選取。這證明該情境後來能提供 UIA，不能直接判定整個 App 不支援；是否為 App 無障礙樹延後啟用仍是推測，尚無冷啟動實機重現證據。

主視窗完整紀錄還包含成功後再次不支援的情況。程式原先向上找 16 層，尚未走到目標 HWND 就會丟掉整個候選分支；32 層 GroupBox fixture 已在原邊界重現失敗。祖先上限改為 64 層，仍須確認目標視窗歸屬，仍由隔離 helper 的逾時限制阻擋卡死。這是獨立確認的探測缺陷，尚未證明使用者 ChatGPT 的實際節點深度。

沿用已確認的原生優先方向。方案比較：只調整錯誤訊息不能接住同一次選取；強制剪貼簿回退沒有經驗證策略；採用有上限的原生重新查詢，處理暫時沒有介面的情況。

## 行為

- 初次查詢成功時立即呈現，不增加固定等待。
- 只有 `unsupported` 可以重試，間隔 120／250／500 ms，最多初次加三次；整組原生請求共用 2 秒預算，每個 helper 呼叫仍最多 1.5 秒。
- 第一次不支援時可對目標視窗直接子節點作一次唯讀查詢，促使按需產生的 provider 有機會就緒；不遍歷桌面或整個文件樹，不讀取整份對話。
- 每次重新取得焦點／滑鼠位置對應的 UIA 元素，不沿用上次失敗的元素。保留原有手動／自動的選取來源範圍。
- 無選取、密碼、逾時、provider 錯誤、目標失效或忙碌立即停止。等待期間有新輸入、取消或前景／程序身分改變也停止，不在新目標呈現舊選取。
- 已辨識 Sublime 保持一次 UIA 後直接依已啟用策略回退，避免多出原生等待。其他 App 不新增剪貼簿資格。
- 只有仍然有效的請求才顯示「正在等候選字介面就緒」；耗盡時訊息說明目前尚未取得介面，避免宣稱永久不支援。診斷只記錄次數／狀態／耗時，不記錄內容。

## 驗證與界線

用可注入讀取函式、時鐘與等待的測試驗證：不支援後成功、終止狀態不重試、重試／總預算上限、等待中取消與目標變更、舊結果不被採用、Sublime 不多等。另以獨立 fixture 模擬 UIA TextPattern 延後公開，走真實 helper／控制器確認同一個請求可成功及沒有剪貼簿變動。

ChatGPT 桌面 App 的冷啟動首筆需要使用者回測；不把模擬 provider 通過寫成已修好所有 ChatGPT 首次啟動情境。

參考：[Electron Accessibility](https://www.electronjs.org/docs/latest/tutorial/accessibility) 說明輔助工具可能觸發自動啟用；[Microsoft Obtaining UI Automation Elements](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-obtainingelements) 說明從焦點、滑鼠位置、視窗與限定子樹取得元素。這些資料不證明使用者這一次失敗的確切原因。
