# SnapBar 統一版本識別設計

日期：2026-11-16。使用者已核准採用「語意版本＋預覽序號」，保留每次 main push 自動發布預覽版的節奏，並同意補齊比較基準、重跑優先順序、版本通道及共用驗證規則。本文件為實作與驗收依據。

## 目標與現況

使用者下載的版本，必須就是「關於與支援」看到的版本。公開版本使用同一份識別資料貫穿版本選擇、建置、打包、驗證與發布。

目前 `.github/workflows/release.yml` 會選出 `v0.1.0-rc.N`，但 `scripts/package-release.ps1` 只把版本傳給 ZIP 命名，沒有傳給 `scripts/build.ps1` 的建置與兩個 publish。`SettingsSupportPage` 讀取 `AssemblyInformationalVersionAttribute`，因此仍可能顯示 SDK 預設的 `1.0.0`。這次修正資料傳遞與發布驗證，保留既有桌面測試證據、來源指紋、選取安全及附件不可覆寫保護。

## 版本規則

公開版本使用 `major.minor.patch`，預覽版加上 `-rc.N`，數字不使用前導零。

- patch：修正問題與相容的維護更新，例如 `0.1.0` → `0.1.1`。
- minor：新增功能，例如 `0.1.0` → `0.2.0`；在 0.x 階段，不相容變更也升 minor 並在更新說明交代。
- major：1.0 之後的重大不相容變更；首次 1.0 是明確的產品發布決定。

main push 繼續自動選擇目前系列的下一個 `rc.N`。遠端 tags 與 Releases（含草稿）中已占用的序號均參與比較，依整數取最大值加一，保留同一 workflow run 已建立 Release 的版本恢復機制。不同系列的預覽序號互相獨立；失敗可以留下空號，已發布版本不可重新指派或覆寫。

正式版必須由維護者明確發布，不因日常 push 自動轉正。正式發布 `0.1.0` 後，維護者必須先將開發系列調整為例如 `0.1.1` 或 `0.2.0`，再分配後續預覽版。版本選擇必須依下列順序處理：

1. 先以 workflow run ID 尋找既有 Release（含草稿），核對唯一性、來源 SHA、版本格式及自動預覽版歸屬標記。歸屬不符或多筆符合均停止，不可重新分配版本來避開衝突。
2. 若找到合法的既有 Release，恢復其版本與原始發布上下文，再執行原有附件、來源及完整性檢查；不因目前系列已有正式版、較新 rc 或不同系列而阻擋。已公開的 Release 不重寫內容或重新發布；既有草稿可在驗證成功後完成原發布。
3. 僅在沒有既有 Release、需要分配新版本時，檢查目前系列的精確正式版 Tag（例如 `v0.1.0`）或已公開正式 Release 是否存在；存在即阻擋並提示調整系列。沒有建立 Release 的早期失敗不算已保留版本，重跑時仍走新版本分配規則。

例如 run A 的 `rc.12` 已公開、網站部署失敗，之後 `0.1.0` 已公開：重跑 A 應沿用 `rc.12` 及原 artifact，官網仍依既有規則選最新完整公開下載；新 run B 則必須調整系列才可分配新 rc。

版本系列集中於根目錄 `Version.props`，初始為 `0.1.0`。MSBuild 與 PowerShell 版本選擇都讀取此檔，不再在腳本寫死系列。明確指定的人工 Release 版本由該 Release tag 決定，不以目前開發系列覆蓋。

## 使用者可見內容

以下 `rc.12` 僅為範例，實際序號延續遠端既有紀錄。

| 位置 | 呈現 |
| --- | --- |
| GitHub Tag | `v0.1.0-rc.12` |
| GitHub Release 標題 | `SnapBar 0.1.0-rc.12` |
| 下載檔 | `SnapBar-v0.1.0-rc.12-win-x64.zip` |
| 官網下載區 | `0.1.0-rc.12 · 預覽版` |
| 關於與支援 | `版本 0.1.0-rc.12`，另標示「預覽版」 |
| 診斷區 | 完整版本及來源 commit |

`v` 是 Tag 與既有下載檔名的前綴，不屬於程式內版本。官網繼續從最新完整公開 Release 取得下載版本，不自行推算序號。正式版標示「正式版」，不加 rc。

本機沒有指定發布版本時顯示 `<目前系列>-dev` 並標示「開發版」。其他分支的 CI 產物沿用 `0.0.0-ci.<run number>.g<commit 前綴>`，標示「測試版」，維持只提供 artifact。人工演練的 `0.0.0-validation` 同樣標示為測試版。繁中與英文資源必須同步更新。

版本後綴採以下完整分類，先排除 `+` 後的來源中繼資料，再依表格判定；比對區分大小寫，不以部分字串猜測通道。

| 版本條件 | 介面通道 | 公開 Release |
| --- | --- | --- |
| 合法版本且沒有預發布後綴 | 正式版／Stable | 必須標為非 prerelease |
| 後綴恰為 `dev` | 開發版／Development | 拒絕，僅供本機建置 |
| 後綴符合 `ci.<正整數>.g<12 位小寫十六進位 SHA 前綴>`，或恰為 `validation` | 測試版／Test | 拒絕，僅供 artifact／演練 |
| 其他合法的非保留後綴，例如 `rc.12`、`beta.1`、`alpha.2`、`preview.3`、`custom.1` | 預覽版／Preview | 必須標為 prerelease |
| 使用 `dev`、`ci`、`validation` 作為第一個識別段，但不符合上述保留格式 | 無效版本 | 建置／打包／發布均拒絕 |

主版本三段及後綴須符合 SemVer 2.0.0：數字識別段不可有前導零，識別段不可為空。main 自動發布只產生 `rc.<正整數>`；人工發布可使用其他合法非保留後綴。外部 Tag 不接受 `+` 中繼資料，來源 SHA 由建置流程附加。人工 Release 的 prerelease 旗標與後綴分類不符時，在附檔前拒絕；未知但合法的非保留後綴一律視為預覽版，不可回退成正式版。程式遇到無法解析的組件版本時顯示「未知版本／Unknown version」，診斷區保留原始資訊，不將其標為正式版。

長串 commit 不佔用主要版本標籤，保留於既有診斷區與 tooltip。程式顯示自身組件內的版本，不查詢網路來替換成官網最新版。

## 建置與版本資料流

1. Action 選出唯一的發布 Tag，沿用目前環境變數傳遞方式。
2. `package-release.ps1` 驗證 Tag，去除唯一的 `v` 前綴，將版本明確傳給 `build.ps1`。明確的無效版本應立即失敗，不可回退為 dev。
3. `build.ps1` 將相同版本傳給 solution build、App publish 與 Probe publish；一般本機 build 使用集中設定的 dev 預設值。相依的自有組件沿用相同版本屬性。
4. 使用 .NET 的 `Version` 與 `InformationalVersion` 寫入版本；`InformationalVersion` 保留完整公開版本與來源 commit。確保來源 commit 僅附加一次，App／Probe 都使用相同來源 SHA。
5. 「關於與支援」讀取組件資訊，主要標籤去除 `+` 之後的建置中繼資料，保留完整 `-rc.N`。版本通道依上表決定，不依 Debug／Release 組態判定；其他合法後綴仍保留原文。
6. ZIP、checksum、Release 與官網沿用同一個發布 Tag。不得靠替換 UI 常數或發布後重新命名 ZIP 修補差異。

Windows 的 `AssemblyVersion`／`FileVersion` 是數字欄位，不承擔 rc、dev 等完整文字識別。對外核對採用完整 `InformationalVersion`／ProductVersion；診斷資料不得把數字欄位誤當成下載版本。

本機桌面測試仍針對相同來源完成，不要求本機預先知道遠端 rc 序號。雲端以既有確切 commit 桌面證據為基礎，另執行寫入發布版本後的既有 smoke 與套件一致性檢查，不削弱任何原有門檻。

## 發布與失敗保護

發布前必須實際讀取打包結果中的 App／Probe 組件中繼資料，核對完整版本（去除來源中繼資料後）與預期 Tag 相符，並核對來源 commit 與預期來源 SHA 相符。檢查需涵蓋 ZIP 內的組件，不能僅相信建置命令參數、檔名或新寫入的宣告檔。

跨 runner 下載後保留既有 SHA-256 驗證，並在發布附件前核對 ZIP 中的版本與來源。人工 Release 附件也適用相同檢查。缺少組件、無法讀取版本、App／Probe 版本不同、來源不同或版本不符均立即停止，不公開自動發布草稿、不上傳錯誤套件。

PowerShell 工具共用一份版本解析與套件驗證模組，不在各 workflow 工作複製解析、組件讀取或比較邏輯。建置 staging 在取代本機套件前驗證 App／Probe；ZIP 建立後及跨 runner 發布前使用同一驗證器的 ZIP 入口，僅讀取目標組件中繼資料，不為不同關卡建立不同檢查規則。SHA-256 負責位元組一致性，版本／來源檢查負責產物身分；兩者不能互相替代。預期版本與 SHA 必須來自 workflow 的固定上下文，不能從待驗證套件自行取得。介面通道分類與工具以相同有效／無效版本案例驗收，避免兩端對同一後綴有不同解釋。

套件 staging 驗證亦應在取代 `artifacts/p0` 前完成，失敗保留前一個套件。讀取組件使用中繼資料，不啟動 App／Probe；暫存資料限制在本次 artifacts 目錄，避免鎖住執行檔或沿用舊產物。

同一 run 失敗重跑優先沿用已驗證 artifact。已發布附件不可覆寫；版本與來源相同但 ZIP 位元組不同時，仍遵守既有 digest 衝突拒絕。既有公開 Release、Tag、附件與發布說明保持不變，從下一個新版本開始套用。

## 更新說明比較基準

版本序號分配與更新說明基準選擇分開處理。基準不受目前版本系列限制，必須依下列規則得到唯一結果：

1. 讀取完整 Releases 清單及來源 Git 歷史。候選只包含有合法公開版本 Tag、已公開且 ZIP／checksum 附件完整的 Release；排除草稿、目前待發布版本及不支援的內部版本。沒有 Release 的單獨 Tag 只保留版本號，不可作為更新說明基準。
2. 將各候選 Tag 解參照至確切 commit；以該 commit 是否為本次來源 commit 的祖先（包含相同 commit）篩選。Tag 無法解析、歷史不完整或缺少有效公開時間時先補取資料，仍無法驗證則停止，不可默默略過。不能只信任 `target_commitish` 的分支名稱。
3. 移除其 commit 為另一候選 commit 嚴格祖先的候選，留下拓撲上最近的公開來源。若留下不同且互非祖先的多個 commit，停止自動選擇並要求維護者以 `PreviousTag` 明確指定；版本解析入口需支援此參數，並將驗證後的結果傳給既有發布入口。指定值仍必須通過候選條件及來源祖先檢查，不可跳過更新說明驗證。
4. 同一 commit 有多個 Release 時，先選正式版，再以 `published_at` UTC 由新到舊排序，最後以完整 Tag 的 ordinal 字典序由小到大決勝。這個順序僅用來決定更新說明基準，不改變官網既有的下載版本選擇規則。
5. 僅在專案從未有任何完整公開套件時，才允許沒有基準並使用首次發布邏輯。已有完整公開套件卻沒有可驗證的祖先基準時停止，不將它當成首次發布。

新建自動發布草稿時，必須一併保存已選定的 `previousTag`（首次發布保存明確的空值）、來源 SHA 與 run ID 作為固定上下文；恢復同一 run 時沿用此上下文，不依之後新增的 Release 重新計算。若恢復本次機制上線前的舊 Release 而沒有基準標記，已公開版本沿用既有內容且不重新彙整；舊草稿若需要重新產生說明，必須先由維護者提供可驗證基準。既有公開內容不補寫標記。

例如 `0.1.0-rc.12` 與 `0.1.0` 指向相同 commit，首次發布 `0.2.0-rc.1` 時以 `0.1.0` 為基準；若它們指向不同 commit，先依祖先關係決定最近來源。此流程不得重新彙整所有已發布說明，也不得默默跳過桌面更新說明檢查。

## 驗證與交付

- 版本選擇：既有 rc 接續、數字排序、草稿／Tag 占號、同 run 恢復、切換系列後從 rc.1 起，以及正式版已存在時僅阻擋新版本分配。補上正式版發布後恢復舊 run、既有草稿恢復、歸屬不符拒絕、沒有草稿的早期失敗重跑等案例。
- 比較基準：跨系列接續、多個祖先選最近來源、同 commit 正式版優先、同通道依公開時間與 Tag 決勝、合併後不同來源互非祖先時停止、明確指定基準仍需驗證、歷史缺漏與找不到祖先時拒絕，以及只有首次發布可無基準。同 run 重跑必須保留原基準，不受之後新增的 Release 影響。
- 通道分類：驗證正式版、rc、dev、ci、validation、beta、alpha 與未知合法後綴；驗證保留前綴的錯誤格式、前導零、空識別段與非法字元拒絕；驗證人工 Release 旗標不符時拒絕，以及介面遇到無效中繼資料不回退成正式版。
- 實際建置：確認預設 dev、明確 rc、正式版本與 CI 版本皆寫入 App／Probe，並確認切換版本重建不會沿用上次中繼資料。
- 套件拒絕：用實際建置組件建立測試 ZIP，驗證錯誤版本、錯誤來源、App／Probe 不一致與缺漏檔案都不能發布；保留原有 ZIP 與 checksum 測試。
- 介面驗收：中英文「關於與支援」皆顯示正確版本與通道，診斷區仍可取得完整版本及來源。下載 `rc.N`、解壓後開啟設定必須看到相同 `rc.N`。
- 執行相關自訂 console runners、PowerShell 發布工具測試及 `scripts/check.ps1`；UI 與發布變更仍需現行桌面 Release 驗證，記錄於 `docs/p0-validation.md`。未完成真實雲端執行時不得宣稱 Action 已端到端驗證成功。

實作時新增唯一的繁中 `release-notes/2026-11-16-unified-version.json`，說明使用者能從下載版本直接對照設定頁版本，以及更新後如何確認；更新 `docs/development.md` 的升版、通道與驗證操作說明。本設計文件本身不變更程式、工作流程或發布產物。
